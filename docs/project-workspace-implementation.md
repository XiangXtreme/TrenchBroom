目标是把 TrenchBroom 从“一个地图对应一个编辑窗口”演进为“一个工程对应一个工作区”。
工程工作区负责地图、资源、编译配置和历史；地图标签负责单张地图的编辑视图。共享资产库
仍然是工程外的独立文件夹，`.tbproj` 只保存项目实际使用到的资源快照和项目内容。

## 1. 已确认的产品决定

以下内容来自需求讨论，实施时视为产品约束；与下文的技术建议分开处理。

| 领域 | 已确认行为 |
| --- | --- |
| 工程窗口 | 一个工程一个主窗口；同时打开多个工程时使用多个主窗口 |
| 地图标签 | 一个工程可打开多张地图，地图以主窗口内的标签显示，并保留各自编辑状态 |
| 内容浏览器 | 默认停靠在底部，可折叠、移动、浮动；统一显示地图、纹理、模型、Sprite、声音、天空盒和预制件 |
| 资源来源 | 浏览器明确区分工程内容、共享资产库和本机游戏资源 |
| 打开资源 | 双击地图打开或聚焦地图标签；双击其他资源打开预览或设置标签；拖入地图才应用或放置 |
| 资产库 | 资产库是独立文件夹，不是 `.tbproj`；欢迎页和工程内都能进入同一套管理界面 |
| WAD/图片 | 可批量导入 WAD，默认按 WAD 名称分组；非 BMP 图片导入后转换为 GoldSrc 兼容格式，并保留原图和转换信息 |
| 使用快照 | 浏览或预览不自动写入项目；地图实际使用资产库资源时立即捕获当前修订到 `.tbproj` |
| 外部更新 | 项目使用内嵌快照，即使资产库变化或不可用也能打开；检测到更新时提示用户，必须显式确认才更新 |
| 更新范围 | 重新导入或更新保留项目资源身份，所有引用一起更新；历史仍可恢复旧修订 |
| 工程规模 | 一个工程对应一个游戏，首版以 Counter-Strike 1.6 验证；几张到十几张地图、几百 MB 资源 |
| 发布 | 继续兼容现有 GoldSrc 游戏/引擎，只修改 TB 和 hltools；BSP 是发布运行产物，不是工程容器 |
| MAP | 直接打开 `.map` 进入临时工作区，保留普通 MAP 保存方式，也可另存为 `.tbproj` |
| 保存 | `.tbproj` 的 `Ctrl+S` 保存整个工程，包括其他地图标签中已经保留的修改 |
| 关闭标签 | 关闭有修改的地图标签只关闭视图，项目继续保留地图修改；保存工程时一起写入 |
| 版本 | 首版支持版本节点、比较和恢复；版本节点覆盖工程整体状态 |
| MCP 目标 | 每次 MCP 调用默认操作“当前活动地图”；目标在该次调用派发时解析并冻结 |
| MCP 显式目标 | 仍支持显式工程和地图目标；显式目标与默认目标不匹配时拒绝，不静默改写 |

“关闭标签但保留修改”只适用于工程中的地图文档。独立 MAP 临时工作区仍遵循其普通
保存/丢弃语义，不能因为复用标签控件而悄悄把修改藏起来。

## 2. 目标使用体验

### 2.1 欢迎页和工程窗口

欢迎页提供“打开工程”“新建工程”“打开 MAP 临时工作区”“资产库管理”。打开 `.tbproj`
后创建一个项目主窗口，窗口标题和状态栏显示工程名、游戏目标及脏状态。项目窗口内部包含：

- 地图标签区：标签名、地图脏标记、关闭按钮、恢复已关闭地图入口。
- 中央编辑区：当前地图的 2D/3D 视图和工具。
- 底部 Content Browser：项目、共享资产库、游戏资源三个来源可切换，并支持搜索、筛选、分组、预览和拖放。
- 现有 Inspector、Outliner、Issue Browser、控制台等面板：它们跟随当前地图上下文，但不拥有地图文档生命周期。
- 工具栏、菜单和状态栏：区分地图命令、工程命令和资源库命令。

切换地图标签只切换编辑上下文，不销毁地图文档。每张地图保存自己的选择、工具、相机、
视图布局、撤销栈和脏状态。预览资源时可以打开预览标签，但预览标签不能让地图编辑命令
意外转向一个不可见或未选择的地图。

### 2.2 资源浏览和使用

内容浏览器中的资源有清晰的来源徽标和状态：工程快照、资产库当前修订、本机游戏资源、
缺失、存在更新、转换失败。资源浏览只查询目录，不因为滚动缩略图或打开预览而捕获资源。

典型流程如下：

1. 用户在资产库中导入 `environment.wad`，系统按 WAD 名称建立默认分组，并为每个纹理条目建立独立资源身份。
2. 用户在地图中将 `brick01` 拖到面上，或在面检查器中选择它。
3. TB 在同一个工程事务中捕获该纹理的当前修订、转换结果、来源和依赖，然后建立地图引用。
4. 用户保存工程；项目即使以后找不到资产库，也能读取该内嵌快照。
5. 资产库重新扫描发现 `brick01` 有新修订时，项目显示“有更新”；用户确认后以一次批量事务更新所有引用。

模型、Sprite、声音和天空盒遵循同一原则。模型的皮肤、`<name>T.mdl` 配套文件、天空盒六面
等可识别依赖应作为捕获闭包一起保存；不能识别的动态字符串依赖要进入诊断而不是猜测。

删除或清理资源前显示使用位置。未使用的快照不能因为一次扫描就自动删除，它们可能被版本
节点、撤销记录或尚未打开的地图引用；清理应是显式工程操作。

### 2.3 关闭、恢复和保存

关闭地图标签时，视图对象可以释放，但地图工作副本仍由工程会话持有。项目目录中显示该
地图仍有未保存修改，重新打开时恢复最新工作副本。关闭工程时统一处理项目脏状态。

建议的工程级操作：

- `Save / Ctrl+S`：提交工程的一致修订，包含所有地图、资源变更和版本节点变更。
- `Save Project Copy...`：导出一致副本，不切换当前工程，也不清除当前脏状态。
- `Close Map Tab`：关闭视图并保留工程修改；提供“重新打开”和显式“卸载/丢弃修改”入口。
- `Close Project`：检查所有工程级修改；保存失败时保留脏状态并报告错误。
- `Create Version...`：把当前工作状态建立为命名节点；版本节点必须覆盖所有地图和共享资源引用。
- `Compare/Restore`：先展示地图、对象、资源和依赖摘要；恢复前自动创建安全节点。

保存和恢复必须使用项目事务。工程文件替换成功前不能显示已保存；中断、磁盘空间不足或
校验失败时保留旧工程和当前工作副本。

## 3. 架构边界

### 3.1 推荐的对象关系

建议引入下列长期对象，名称可按现有代码风格调整：

| 对象 | 所有权和职责 |
| --- | --- |
| `ProjectSession` | 一个工程的工作副本、地图目录、资源快照、历史、编译配置和工程事务 |
| `MapDocument` | 单张地图的几何、实体、选择、工具、相机、撤销栈和编辑状态 |
| `ProjectWindow` | 项目级 Qt 壳、标签工作区、菜单、停靠面板和活动上下文路由 |
| `MapEditorView` | `MapDocument` 的可替换编辑视图；视图关闭不等于文档卸载 |
| `ContentCatalog` | 工程内容、资产库内容、游戏来源的稳定 ID、类型、修订、依赖和查询 |
| `AssetImportService` | WAD/图片/MDL/Sprite/WAV/天空盒导入、转换预览、重导入和依赖捕获 |
| `ProjectStore` | `.tbproj` SQLite 容器、事务、内容块、版本节点和校验 |
| `CompileSnapshot` | 编译开始时冻结的地图、资源和配置；编译期间不跟随编辑焦点变化 |
| `McpExecutionContext` | 一次调用解析出的工程、地图、文档代次和权限；不保存跨调用的隐式地图指针 |

`ProjectWindow` 不应成为新的“大一统资源管理器”。渲染器、GPU 资源和现有地图 manager
仍按有效上下文管理；可共享的 CPU 解码缓存另行设计。浏览器负责查询和入口，目录负责身份
和修订，存储负责持久化，导入服务负责转换，地图文档负责编辑。

### 3.2 从现有代码迁移的落点

当前实现已提供工程存储、资产库、资源快照、版本和编译快照基础，但工作区生命周期仍需
收拢。实现者应先重新阅读最新源码，因为其他工程正在并行修改这些区域：

- `lib/TbProjectLib`：Qt 无关的 `AssetLibrary`、`ProjectStore`、`LibrarySync`、内容哈希、WAD/模型解析。
- `lib/TbUiLib/include/ui/ProjectSession.h` 与对应实现：工程工作副本、地图注册、捕获、保存、历史和编译导出。
- `lib/TbUiLib/include/ui/MapWindow.h`：当前地图窗口仍同时承担文档、视图、面板和菜单职责，需拆出可嵌入编辑上下文。
- `lib/TbUiLib/src/MapWindowManager.cpp`：当前按地图创建完整 `MapWindow`，迁移为项目窗口内创建/切换地图标签的主要入口。
- `lib/TbUiLib/src/ProjectWindow.cpp`：项目关闭和地图关闭策略需要由项目会话统一协调。
- `ModelBrowser`、`ModelBrowserView` 及 Asset Browser：拖放数据必须逐步从发布路径字符串升级为工程/资源 ID 加修订。
- MCP 相关执行器、桥接器和 UI 选择钩子：不得继续依赖 `topMapWindow()` 或跨调用缓存的窗口指针。

第一阶段可保留 MAP 序列化和现有渲染路径。不要用一轮 UI 重写同时替换原生对象树、编译器
和渲染器；先让项目会话正确持有多个地图文档，再逐步迁移资源引用和编辑状态。

## 4. `.tbproj` 与资产库语义

### 4.1 资产库不是工程

资产库是可移动的独立目录，目录内有隐藏的 `.tbassets` SQLite 数据库。资产库可以被多个
工程浏览和引用，但工程不依赖其路径才能打开。库中保存原始内容、兼容结果、转换配方、
内容哈希、来源和依赖。WAD 成员是独立资产，不能因为同一个 WAD 容器被扫描就失去独立版本。

### 4.2 工程保存实际使用的快照

项目使用资产库资源时立即复制当前修订到工程内容块，并写入来源信息：`library_id`、
`library_asset_id`、库修订、库哈希、来源容器/成员、原生格式、转换参数和工程内容哈希。
地图只引用工程资源 ID，不保存“以后从库路径读取”的运行时依赖。

因此资产库更新不会静默改变项目。更新检查比较项目记录的库哈希和库当前目录记录，结果
至少区分 `UpToDate`、`NewVersion`、`Missing`、`LibraryUnavailable`。显式更新时保留资源
身份并批量替换引用；失败时整个批次回滚，旧修订可通过版本恢复。

### 4.3 编译和 hltools

游戏运行只看 BSP 及其运行资源，`.tbproj` 不是游戏输入。TB 在编译开始时导出固定快照：
地图 MAP、只含实际使用纹理的 WAD、`wads.cfg`、资源发布路径和快照清单。hltools 编译
该快照，不读取资产库，也不跟随 TB 当前焦点。现有 hltools 的“将纹理嵌入 BSP”行为保持为
发布阶段行为；是否附加 MAP 源码必须是显式配置，默认关闭。

后续若让 hltools 直接读取 `.tbproj`，也应复用同一个固定快照契约，而不是让编译器耦合
SQLite 表结构。这样可以保证编译输入固定、工具链可独立运行，并保留 MAP/WAD 交换路径。

## 5. 多地图与命令上下文

编辑命令必须先解析一个 `MapEditingContext`，其中至少包含工程 ID、地图资源 ID、运行时
文档代次和可用视图。项目级命令（导入、更新、版本、编译配置）不应伪装成地图命令；地图
级撤销只影响对应地图，工程资源事务单独提交。

标签切换、预览标签、浮动内容浏览器和停靠面板都可能改变 Qt 的焦点，但不能隐式改变所有
命令目标。建议将“当前活动地图”定义为项目窗口中最后一个明确激活的地图编辑标签，并在
状态栏或 MCP inspect 中显示。没有活动地图时，要求显式选择或返回可理解的错误。

编译任务、异步导入、预览生成和资源更新在启动时捕获项目/地图/资源修订。完成回调必须
检查会话仍然存在、修订没有被替换、目标没有被卸载；过期结果丢弃或要求用户重新执行。

## 6. MCP 适配要求

MCP 继续遵守现有四入口契约：`tb_inspect`、`tb_api`、`tb_execute_python`、`tb_capture`。
不要新增一套项目专用工具、旧 IR、跨调用 sticky selector 或兼容包装层。

### 6.1 默认目标是每次调用重新解析

用户已明确选择：MCP 每次调用默认操作当前活动地图。具体规则：

1. 请求进入派发器时解析当前工程窗口和活动地图。
2. 将工程 ID、地图资源 ID、文档生命周期代次和所需视图写入本次执行上下文。
3. 执行期间用户切换标签、打开预览或切换项目，不改变本次调用目标。
4. 若调用带显式项目/地图目标，则校验目标存在且允许访问；不匹配时拒绝，不回退到当前地图。
5. 下一次调用重新解析当前活动地图，不沿用本次调用的隐式目标。

`executionId` 去重必须把解析后的目标纳入请求身份。重复请求即使焦点已经改变，也只能重放
原始回执，不能把同一编辑再次应用到另一张地图。文档关闭、卸载、重载或代次变化时，句柄
必须失效；仅关闭标签视图不应让仍由项目会话持有的文档句柄失效。

### 6.2 inspect、execute 和 capture

- `tb_inspect` 返回有界的工程列表、活动地图、打开/保留的地图文档、标签脏状态和可用视图；大内容必须分页或摘要。
- `tb_execute_python` 通过原生文档守卫和事务执行 Python；脚本组合场景，C++ 保留文档身份、句柄生命周期、命令和回滚。
- `tb_capture` 必须报告实际工程、地图、视口、投影、相机和尺寸。隐藏地图若没有可用视口，必须明确失败或按已定义策略先显示目标，不能伪造截图。
- 地图事务只保证地图编辑回滚；工程资源更新、文件系统、编译进程等外部效果必须在回执中如实报告，不能承诺跨边界原子回滚。

Python 上下文应引用工作区/文档/视口能力，不通过 `MapWindow*` 查找目标。保留的文档可在
没有可见标签时执行不依赖视口的编辑；需要视口的动作应给出明确错误。API 发现、权限、预算、
主线程和 loopback 约束沿用 `docs/mcp-development-governance.md`。

## 7. 分阶段实施顺序

### 阶段 A：工作区骨架

- 为项目会话建立稳定的地图目录和运行时文档生命周期。
- 将地图编辑器控件从 `MapWindow` 中抽出为可嵌入的 `MapEditorView/Context`。
- 在一个 `ProjectWindow` 内实现地图标签、激活、关闭视图和重新打开。
- 保持现有单地图路径可用，暂不改变 MAP 序列化和渲染器。
- 加入“标签关闭不卸载文档”的保存、恢复和脏状态测试。

### 阶段 B：统一内容浏览器

- 让浏览器查询工程目录、资产库目录和游戏来源，并显示来源/修订状态。
- 把拖放载荷改为稳定资源 ID、修订和目标上下文；路径只作为导入或发布映射。
- 为纹理、模型、Sprite、声音、天空盒和地图接入双击预览/打开与拖放行为。
- 资源实际使用时执行捕获闭包，并让捕获和放置具有明确的失败回滚。

### 阶段 C：保存、历史和编译

- 统一工程保存、另存副本、自动恢复、版本节点、比较和恢复的事务边界。
- 完成资产库更新检查、批量更新、回滚、缺失资源诊断和显式清理。
- 所有编译任务使用冻结快照；补齐 CS 1.6 的发布路径、WAD、模型/Sprite/声音和天空盒依赖验证。
- 保留现有 MAP/WAD 导出作为兼容和故障排查路径。

### 阶段 D：MCP 和插件迁移

- 将执行上下文从窗口查找迁移到工作区/文档能力。
- 为默认当前地图、显式目标、标签关闭、重复请求和文档代次编写回归测试。
- 更新 API 发现、示例、控制台/插件入口、capture 和 MCP skill；如 skill 源有改动，执行仓库规定的同步检查。
- 做一次完整架构切换和最终验收，删除旧 MCP 专用状态，而不是长期维护两套语义。

## 8. 验收矩阵

| 场景 | 验收结果 |
| --- | --- |
| 同一工程打开三张地图 | 三个标签各自保留选择、相机、工具和撤销状态，切换不重载文档 |
| 关闭带修改标签后保存工程 | 关闭的是视图；保存后重新打开地图仍有修改 |
| 关闭标签后显式卸载 | 用户看到脏状态和丢弃确认；卸载后旧句柄失效 |
| 资产库导入 WAD | 纹理按 WAD 分组，条目独立身份，可预览转换结果 |
| 将库纹理用于两张地图 | 两张地图均引用同一工程快照；资产库不可用时仍可打开项目 |
| 库纹理有新修订 | 项目显示更新提示；确认后所有引用一起更新，取消不改变旧快照 |
| 双击模型/声音/天空盒 | 打开预览或设置标签；只有拖入地图才产生地图引用 |
| 项目编译 | 快照固定；编译过程中切换标签或修改项目不改变该次输入 |
| 直接打开 MAP | 进入临时工作区，普通 MAP 保存不被工程关闭规则覆盖，可另存项目 |
| MCP 无显式目标 | 每次调用解析当时的活动地图，执行中切换标签不影响目标 |
| MCP 显式目标 | 目标不存在、代次不符或权限不足时拒绝，不静默改用活动地图 |
| MCP 重放请求 | 焦点改变后重复 `executionId` 只返回原始回执，不修改第二张地图 |
| MCP capture | 回执包含真实工程/地图/视口；隐藏地图不可捕获时明确失败 |
| 崩溃/中断保存 | 旧工程可恢复，未提交工作副本仍标脏，不能显示虚假的成功状态 |

## 10. 主要风险和明确边界

- SQLite 单文件解决存储一致性，不自动解决大工程增量保存、历史清理、损坏恢复和并发编辑；这些需要单独压测和故障测试。
- 资产库快照解决路径丢失和外部更新问题，但不能自动推断脚本、实体字符串或未知动态依赖；必须提供诊断和手工声明入口。
- 地图标签是视图组织方式，不应让地图文档生命周期重新绑定到 QWidget；否则关闭标签会破坏撤销、MCP 句柄和未保存内容。
- 工程级资源事务和地图撤销事务边界不同；不要把跨地图更新伪装成单张地图 undo，也不要承诺外部编译进程可回滚。
- 参考 UE 时只借鉴 Content Browser、Asset Registry 和项目级工作区的职责分离；不引入 UE 的对象包格式、目录结构或运行时对象系统。
- `.tbproj` 面向编辑和分享，BSP 面向游戏运行；两者通过固定编译快照连接，不能把工程元数据无条件塞入 BSP。
