# TB 原生工程格式设计草案

状态：工程容器、独立资产库、工程资源快照与编译快照导出已实现；下文仍包含后续目标设计。
2026-10-29 更新。试用入口与当前限制见 [工程使用说明](native-project-usage.md)。

## 当前实现边界

- `.tbproj` 使用 SQLite，包含多地图、资源原件与兼容结果、不可变修订和命名版本。
- 工程会话拥有编辑工作副本，保存时包含所有已打开地图；成功后原子替换工程文件。
  比较、创建版本和保存副本包含未保存地图的当前内容，且不误将原工程标记为已保存。
- 导入、重导入、重命名和虚拟移动通过工程服务执行。稳定资源 ID、内容修订和
  首次导入的游戏路径分别保存，目录移动不会改变现有游戏引用。
- 现有 Asset Browser 接入工程目录，显示地图、纹理、模型、Sprite、声音与预制件；
  双击地图打开，模型/Sprite/声音保持现有放置行为，纹理在面检查器中选用。
- GoldSrc 图片导入预览确认后生成 WAD3，保留原图及转换配方；项目 WAD 自动挂载，
  重导入后更新已打开地图。其他原生资源目前按文件保存，未声称完成引擎兼容验证。
- 命名版本支持目录/内容/依赖层面的比较和整体恢复，恢复前自动建立安全版本。

地图目前作为 MAP 文档内容存储，尚未迁移到原生对象树；对象独立旋转/缩放、
跨地图模板实例及覆写仍待实现。实体定义快照、编译配置与发布流程、自动依赖捕获、
使用位置界面、组合天空盒及模型配套文件的自动导入也尚未完成。
目前完整保存会复制一致快照，几百 MB 工程的增量保存与历史清理性能仍需后续实现。

## 已确认的产品决策

- 首版以现有 Counter-Strike 1.6 游戏/引擎验证，只修改 TB 和 hltools。
- 一个工程对应一个游戏，包含多张地图、共享资源和多套编译配置。
- 典型规模为几张到十几张地图、几百 MB 资源，主要由个人编辑，分享整个工程文件。
- 日常保存和分享使用一个完整工程文件。
- 使用的纹理、天空盒、模型、Sprite、声音及配套依赖内嵌管理。
- 图片导入自动生成兼容结果，预览确认后采用；额外保存原图以便重新转换。
- 内嵌副本是权威来源，外部修改通过手工重新导入应用。
- 重新导入保留资源身份，所有引用一起更新。
- 预制件跨地图联动，修改模板可更新实例，允许实例局部覆写。
- 第一版版本管理支持版本节点、比较与恢复。
- hltools 的 MAP 源码附加功能已改为显式开启；工程保存与游戏发布分别设计。

以下结构与实施顺序是技术建议，并非用户已经逐项确认的格式规范。

## 工程的内容与身份

工程保存游戏目标、实体定义快照、地图目录、资源库、模板库和编译配置。
地图保存对象树、几何、材质绑定、实体属性、变换、枢轴、图层与编辑状态。
游戏安装路径、编译器可执行文件位置和个人快捷键由本机配置负责。
换电脑后，编辑资源和地图不依赖原机路径；实际运行游戏仍需配置本机安装。

项目、地图、节点、资源、模板与模板子对象使用稳定 ID。显示名称、发布路径、
内容哈希分别建模：内容相同可以共用存储，但不同资源的身份和替换行为仍独立。
现有对象的 link ID 表达关联关系，不直接充当全工程唯一节点 ID。

核心记录建议分为：

| 记录 | 职责 |
|---|---|
| 工程与版本 | 工程身份、格式版本、所需能力、游戏目标 |
| 地图与节点 | 按地图分区的对象树、几何、属性和编辑状态 |
| 资源与内容块 | 资源身份、原文件、兼容结果、内容哈希 |
| 转换配方 | 转换器版本、尺寸、调色板、透明处理等参数 |
| 依赖与引用 | 地图引用、资源配套依赖、手工声明的动态依赖 |
| 模板与实例 | 模板修订、实例关联、子对象身份和覆写 |
| 编译配置 | 选项、工具版本记录、发布目标及路径映射 |

## 工程与统一内容管理

工程成为地图和共享内容的顶层所有者。参考 UE 的 Content Browser 与 Asset
Registry 分工：浏览器负责呈现与操作入口，资源目录负责未加载内容的查询和身份。
TB 按自身的单文件工程、GoldSrc 发布要求设计存储与引用，不引入 UE 的对象系统。
本节是架构建议，具体类型名与交互仍待原型验证。

| 层次 | 职责与边界 |
|---|---|
| 工程会话 | 当前工作修订、地图目录、共享内容、工程事务、历史和编译配置 |
| 内容目录 | 稳定 ID、类型、显示名、虚拟文件夹、标签、修订、兼容性和依赖查询 |
| 导入与转换 | 依赖发现、预览确认、转换配方、重新导入，以及失败时保留旧修订 |
| 内容存储与解析 | 按修订读取原件和兼容结果，校验内容块，提供字节流或受管理文件 |
| 文档与类型服务 | 地图编辑、模板编辑、纹理参数、模型/Sprite/声音等各类型的操作 |
| 浏览器与选择器 | 查询目录，呈现缩略图、筛选、使用位置和命令，不直接写存储表 |
| 预览与渲染缓存 | 按需解码和上传，跟随资源修订与渲染上下文失效，可重新生成 |
| 编译与发布 | 固定工程快照，解析依赖，将内部引用映射为 GoldSrc 名称与路径 |

地图、纹理/材质、模型、Sprite、声音、天空盒和预制件在同一内容目录中组织。
地图作为有专门编辑器的文档参与浏览与依赖查询；不把地图对象树塞入普通二进制
资源记录，也不要求打开所有地图才能浏览资源。天空盒、动画纹理组和配套模型
文件可作为组合资源，目录表示逻辑内容，存储层管理其多个内容块。

虚拟文件夹只用于组织，例如“场景/工业区”，不要求对应磁盘目录或游戏发布路径。
重命名、移动保留资源 ID。纹理像素数据与面上的贴图参数分别管理；首版材质绑定
表达 GoldSrc 可发布语义，未来扩展额外通道时也应明确目标引擎能力。

引用保存工程身份、目标 ID 及必要的类型信息；当前工作状态解析当前资源修订，
历史节点与编译快照解析固定修订。引用位置索引覆盖面材质、已知实体资源属性、
模板及资源配套文件，能够回答“哪些地图/对象使用它”。未知字符串不能自动当成
资源引用；动态加载的依赖提供显式声明入口。类型依赖要校验循环，不以统一目录
为理由允许任意资源互相包含。

共享资源更改发出带修订的事件，更新已打开地图与预览；未打开地图保留稳定引用，
重新打开时解析新修订。删除先展示引用位置，提供替换、取消或显式保留缺失引用；
不静默删除地图对象，也不在外部目录找到同名文件后悄悄替代缺失资源。

### 现有 Asset Browser 的演进

复用当前文件夹导航、搜索筛选、缩略图布局、模型/Sprite 预览、声音试听和拖放。
接入内容目录后，逐步增加地图、纹理/材质与天空盒，并提供以下工程操作：

- 导入、重新导入、转换设置、重命名、移动、复制及带依赖的跨工程迁移。
- 查询使用位置与依赖、预览替换影响、检查缺失或不兼容内容、显式清理未使用资源。
- 双击地图打开文档；拖放纹理用于贴图，模型/Sprite/声音沿用对应放置语义，
  拖放预制件创建关联实例。跨工程拖放先完成依赖迁移，再建立目标工程引用。
- 项目内容与本机游戏资源使用明确的来源标识；后者作为导入来源浏览，不混同为
  已内嵌内容。建议首次使用时捕获所需依赖，图片仍走已确认的转换预览；已有
  MAP 导入先报告未能解析的引用。工程保存和分享可检查尚未内嵌的必要内容。

统一后端不要求取消面检查器中的快速材质选择器。主浏览器和专用选择器查询同一
目录，按使用场景过滤内容，避免两个窗口各自维护资源身份和导入规则。

### 现有代码的迁移边界

当前 `BrowserAsset` 主要保存路径、绝对路径与修改时间，`ModelBrowser::scanAssets`
扫描游戏文件系统或本机目录；`ModelBrowserView` 的拖放数据与预览缓存按路径识别。
新工程模式需要携带工程/资源 ID，缓存键纳入资源修订、转换结果与预览设置；异步
任务提交结果前确认目标修订和会话仍有效，防止旧预览覆盖重新导入后的内容。

`Map` 当前拥有 `GameFileSystem`、`EntityModelManager` 和 `MaterialManager`。
工程接管持久内容及引用解析，地图仍拥有地图编辑状态；现有加载器通过解析接口
读取项目内容。GPU 资源与渲染器保持受资源管理器及有效 GL 上下文约束的生命周期，
不能直接把所有现有 manager 改成全局单例。可共享的 CPU 解码缓存另行评估。

`AssetPreviewProvider` 的 Sprite 路径已支持字节读取；声音试听仍依赖真实磁盘路径，
预制件缩略图也读取外部图片。需要受管理的派生缓存/临时文件适配现有 API，按
内容修订隔离并维护使用期限；这些文件可删除重建，不成为工程权威数据。

传统独立 MAP 工作流继续通过游戏文件系统适配器工作。分阶段替换扫描与解析入口，
先建立工程资源闭环，再迁移共享所有权，避免一次改写全部编辑与渲染代码。

## 对象变换

保存局部几何、对象变换和枢轴，同时保留数值面板的旋转/缩放表达，避免每次
从矩阵重新分解而丢失旋转圈数等编辑意图。MAP 导入使用导入时的几何作为起点，
不猜测无法恢复的历史旋转和缩放。

世界几何由局部几何和父子变换求值，供渲染、拾取和导出使用。面/顶点编辑必须
明确修改哪一层局部几何，不能只在保存时补记数值。零缩放、镜像、非均匀父级
缩放、剪切及纹理锁定要有明确行为，提交变换前验证几何是否合法。
烘焙变换是显式操作，并由同一撤销事务维护几何与变换状态。

## 资源与发布名称

原图、转换配方和兼容结果随资源修订一起保存；转换确认后更新资源并使相关
预览与编译缓存失效。天空盒六面、动画纹理组、模型配套文件作为完整依赖管理。
提供使用位置查询、替换影响预览和显式的未使用资源清理。

内部资源 ID 不直接输出为游戏名称。发布映射必须保留 GoldSrc 纹理特殊前缀、
动画组关系、短名称限制，以及模型、声音等资源的有效游戏路径。同名不同内容
需要显式解决冲突；无法可靠重写的脚本或字符串引用进入诊断，不能猜测改名。

## 预制件与工程级修改

模板是独立定义，实例记录模板修订、变换及按稳定子对象 ID 定位的覆写。
修改模板采用显式模板编辑入口，普通实例编辑默认形成覆写。
支持恢复单项覆写和解除关联。首阶段优先覆盖变换、实体属性和材质覆写；
子对象增删与拓扑覆写需要额外定义冲突规则后逐步补齐。

模板删除了被覆写对象时保留冲突记录，并提供保留、删除或解除关联的处理入口。
重复放置实体组合需要避免 targetname 等内部连接互相串接，同时保留明确的外部
连接；实体引用转换采用已知规则，未知字符串保持原样并提示检查。

共享资源和模板修改属于工程级事务；地图操作保持现有命令语义。跨地图操作
必须整体成功或回滚，并覆盖未打开地图。地图撤销与工程撤销的相互影响需先做
原型验证，防止撤销地图编辑时意外恢复旧的共享内容。恢复日志、自动备份和
运行期撤销记录分别设计，不默认承诺跨重启保存完整撤销历史。

## 存储候选与保存语义

优先验证 SQLite 单文件容器：事务保存变更记录，几何按对象或适当数据块组织，
资源内容按需读取和按内容去重，避免改一个实体就重写全部资源。压缩按内容块
选择，不对已经压缩的资源反复压缩。扩展名暂称 `.tbproj`，尚未定名。

首选验证 rollback journal 的 DELETE 模式，以正常提交后的主文件作为可携带
工程。事务期间可能存在恢复日志；发生中断时由存储层恢复，不能手工删除日志。
编辑器提供生成一致副本的分享/另存入口；正常关闭后可直接复制工程文件。
事务中的普通文件复制不作为一致备份方案。

Ctrl+S 提交完整、一致的工程修订；自动恢复保存到受管理的本地恢复区，恢复后
由用户决定是否写回。保存失败保持脏状态并报告错误，不提前显示保存成功。
历史资源修订按明确保留策略回收，整理空间作为独立操作执行。

容器候选需要验证大资源、小几何更新、磁盘空间不足、中断写入、另存和备份。
SQLite 事务提供存储基础，不能替代项目层的校验、错误处理和故障测试。
当前结论不构成已经完成的性能或可靠性验收。

## 工程版本历史

第一版采用工程内的命名版本节点，提供比较和恢复。以下为建议的具体语义：

- 普通保存更新当前工作状态；创建版本节点由用户显式操作，记录名称、说明和时间。
- 节点记录完整工程的一致状态，包括所有地图、共享资源及其原文件与转换配方、
  模板、实例覆写、游戏目标与编译配置。比较和恢复都不得遗漏共享依赖。
- 历史使用不可变修订和内容块引用，共用未变化的数据。保留节点引用的旧资源
  必须可用，不能被当前资源替换或未使用资源清理覆盖、删除。
- 比较先提供新增、删除、修改的地图、对象、资源、模板及属性摘要；空间叠加等
  可视化比较另作后续交互评估。稳定 ID 用于匹配对象，避免名称变化被误判为重建。
- 恢复前先处理当前未保存内容，并保留恢复前工作状态的安全节点。恢复以同一
  工程事务切换完整状态，保留既有历史节点；单独恢复对象或资源另行评估。
- 节点删除必须显式执行。空间整理仅回收当前状态、保留版本与受保护快照都
  不再引用的数据；自动恢复使用独立保留策略。
- 分享副本建议默认包含当前工程状态及其完整依赖，可选择包含版本历史。
  删除历史的分享副本不应更改原工程。
- 工程内历史、运行期撤销、崩溃恢复与外部备份分别负责长期节点、操作撤回、
  未保存修改恢复与文件级损坏恢复。备份文件必须独立于主工程。

SQLite 的事务与 journal 负责存储一致性，版本节点由应用显式实现。
Git 继续用于 TB/hltools 源码；后续如需要项目 Git 工作流，评估稳定的目录导出
和资源文件映射，再交给 Git/LFS 管理。其导出与回读需要完整保留工程语义。

## TB 与 hltools 的分工

建议抽出不依赖 Qt 的共享工程读取与解析模块，供 TB 和 hltools 使用，统一
版本、引用解析和校验规则。TB 负责编辑、撤销、预览和导入；hltools 从固定
工程修订读取选定地图，将模板和变换展开成可编译数据，并解析工程内资源。
编译期间继续编辑不应改变该次编译的输入。

已实现的第一版用“导出固定编译快照”承担这个边界：TB 是工程内容的唯一写入者，
hltools 无需数据库依赖即可编译快照目录；两者的契约是 `map.map` + `textures.wad`
+ `wads.cfg`，而不是 SQLite 表结构。这保证编译输入固定、不访问资产库，也避免
把工程格式细节耦合进编译工具链。后续若需要 hltools 直接读取工程修订，可复用同一
快照模型，只替换内容来源。

MAP 导入/导出保留，作为交换和兼容途径。首个集成里程碑可先输出临时 MAP/WAD
接入现有编译链，之后再接直接读取；临时产物不承担工程编辑状态的权威保存。
发布只收集所选地图需要的运行资源，原图、编辑元数据和模板定义留在工程中。

## 资产库层

资产库不是 `.tbproj`，而是一个独立目录，内含隐藏目录文件 `.tbassets`（SQLite）。
一个库可以被任意多个工程引用，也可以整体移动到别的盘符：库标识保存在目录文件里，
而不是从路径推导。

- 内容来源：WAD 容器及其每个纹理条目、PNG/BMP/TGA 图片、MDL 及其配套、Sprite、
  WAV、成组天空盒。WAD 条目是独立资源：拥有自己的稳定 ID、内容哈希、修订号和
  可比较身份，改一张纹理不会替换同容器的其他纹理。
- 稳定 ID 由 `tbasset|<libraryId>|<容器相对路径>|<成员名>` 派生；移动库目录、
  重命名成员所在文件不会改变同一份内容的身份。
- 目录表保存 `assets`/`asset_revisions`/`sources`/`content`/`dependencies`。
  内容按 SHA-256 去重，行内只保存引用；修订历史保留每版显示名、虚拟路径、配方
  和内容哈希，便于比较与回溯。
- `dependency_hints` 在扫描时记录资源自己声明的依赖：MDL 的外置动画组
  （`<name>01.mdl` 起，数量取自头部 `numseqgroups`）与分离纹理文件
  `<name>T.mdl`、天空盒六面。扫描结束统一按归一化文件名主干解析成 `dependencies`
  边（`model-animation`、`model-companion`、`skybox-face`），只有真正存在于库中
  的候选才成为依赖，目标丢失时边保留并标记为 missing。
- GoldSrc 模型把纹理**内嵌**在文件里（纹理表后紧跟 miptex 数据），纹理表中的名字
  不是外部图片。早期实现按名字匹配同名 PNG 会误捕获无关资源，已移除；分离纹理
  关系是单向的：`crateT.mdl` 不会反向依赖 `crate.mdl`，否则每次捕获都会成环。
- 天空盒六面各自仍是独立纹理资源；另有一个 `Skybox` 组资源以清单作为内容，
  依赖六张面，捕获时整组进入工程。
- 库的重新扫描是显式操作。工程打开、更新检查都不会扫描库目录，只读取目录表中
  已记录的内容与哈希。

## 工程快照层

`.tbproj` 只保存工程实际使用的资源。绑定库资源时，当前修订的内容立即复制进工程
（快照），地图只引用工程内资源 ID，不再引用库路径。

- 每个快照记录 `library_id`、`library_asset_id`、`library_revision`、
  `library_hash`、来源容器与成员、原生格式与转换参数。这些列与内容哈希一起写入
  修订行，因此同一资源的历史修订各自保留来源信息。
- 工程修订保存的是“兼容结果”的 SHA-256；库资源保存的是“原生内容”的 SHA-256。
  跨层哈希不可直接比较，检查更新时用库当前哈希对 `library_hash`。
- 更新检查返回 `UpToDate`/`NewVersion`/`Missing`/`LibraryUnavailable`。
  库缺失或资源损坏只影响检查结果，不影响工程打开与预览。
- 更新只由用户发起：一次批量更新在单个存储事务内完成，任何一个资源失败则全部
  保持旧修订。更新沿用同一 `project_asset_id`，因此所有地图引用同时生效，旧修订
  仍可恢复。忽略状态按 `(资源, 库哈希)` 持久化，“稍后提醒”只作用于当前会话。
- 资源复用规则：导入时若已有相同虚拟路径且内容哈希、来源、类型一致，则复用修订，
  不会因为重复导入产生新修订。
- 捕获与更新都走同一个捕获计划：先完整准备所有资源与其依赖边，再由
  `ProjectStore::captureAssets` 在单个事务里提交资源修订和依赖图。任何一个依赖
  转换失败则整批不落盘，工程也不会被标记为已修改。计划里只为缺失的依赖创建快照，
  已存在的依赖按 ID 连接，绝不因为库出现新版本而静默改写。
- 捕获计划会**重写**该资源的依赖边，因此库中删除配套文件后，更新时旧的边不会残留。
- 判断“需要更新”同时看内容哈希和依赖图：库只新增/删除了配套资源、主体内容未变时，
  也会刷新主体，使内容与依赖保持一致。

## 编译快照导出

`ProjectSession::exportCompileSnapshot` 把一个工程地图写成固定编译输入目录：

- `map.map`：当前地图内容（含未保存编辑），保持 TrenchBroom 保存格式。
- `textures.wad`：只包含该地图**按名字实际引用**、且已转换为 GoldSrc 兼容格式的
  miptex。导入的整包 WAD 只导出被引用的那几张，而不是整个容器。
- `wads.cfg`：`textures.wad` 一行，供 hltools `-wadcfgfile` 使用；路径为相对
  路径，因此在任意机器上只要在目录内运行编译即可复现。
- `snapshot.txt`：工程 ID、地图资源 ID 与修订、每个资源的发布时间路径、ID、
  修订与内容哈希，以及纹理清单，便于核对“编译的到底是哪一版”。
- 工程依赖闭包（递归 `ProjectStore` 依赖表）一并导出到 `resources/<发布路径>`，
  因此模型会带上分离纹理文件与动画组；清单里每个条目标注 `direct` 或 `dependency`。
- 缺失、歧义、非法路径、扫描失败一律**阻断导出**并列出引用、地图与行号；编译器
  工具纹理（`clip`/`skip`/`hint` 等）与 `gfx/env` 天空盒面记为 `external`，因为它们
  由编译器或游戏本体提供，声称已打包是不准确的。

导出只读取工程快照，不需要资产库；库在导出后被删除也不改变结果。hltools 侧
不需要任何改动：默认行为就是把地图用到的纹理嵌入 BSP（`bsp info` 显示
“embedded”），未使用的资源不会进入 BSP。vis 阶段需要 `.prt`，与快照无关。

## 当前限制

- 地图仍以纹理名/发布路径字符串引用资源，审计、导出与编辑器拖放统一通过
  `ProjectReferenceIndex` 解析：纹理名（大小写不敏感）解析到嵌入它的工程 WAD，
  其余资源解析到发布路径，重复即报歧义。地图文件本身还没有保存资源 ID，同名纹理与
  精确使用位置仍依赖“发布名不变”这一约定。
- 库目录的变化需要显式 rescan（工程窗口或库窗口）。文件监视器只覆盖游戏文件来源，
  所以“库更新后主动提示”尚未实现。
- 图片在**捕获进工程时**才转换，没有复用导入时的预览确认流程；库中保存的是原图。
  想在库里维护已处理好的兼容纹理，需要把转换配方前移到入库步骤。
- 同一资源名来自不同库、内容不同时直接报冲突，尚无图形化冲突合并。
- 天空盒六面按纹理资源快照保存，尚未生成引擎 `gfx/env` 布局的发布产物。
- 依赖边覆盖 MDL 分离纹理/动画组与天空盒；Sprite 帧、WAV 引用等仍按单文件资源处理。
- 库目录移动后需要在工程里重新指向；已捕获快照不受影响。

## 后续：服务边界

当前 `ProjectSession` 同时承担会话协调、依赖递归、格式转换、资源物化和编译打包，
继续加功能难以保证一致性。下一步按三层拆分，存储层与浏览器保持不变：

- 应用级资产库服务：库登记、创建、导入、扫描、变更通知（含文件监视）。
- 工程资源服务：捕获计划、更新、依赖图与事务（把 `captureAssets` 之上的逻辑从
  `ProjectSession` 移出，会话只保留协调职责）。
- 引用解析与发布服务：地图引用 → 资源 ID 的解析、依赖闭包、冲突检查与固定编译输出。

## 现有代码基础

- `mdl::Group` 已有变换矩阵，`NodeSerializer::groupProperties` 已保存分组变换。
- `LinkedGroupUtils` 已有同地图关联更新和实体 protected properties，适合评估
  复用算法，但不是已经实现的跨地图模板与通用覆写系统。
- `BrushNode` 当前以 `Brush` 几何为核心，独立对象变换需要覆盖编辑命令与求值。
- TB 的 `ZipFileSystem` 是读取基础；hltools 的 `create_zip` 当前在内存中构建
  整个 ZIP。二者不直接满足增量工程保存要求。

## 建议的交付顺序与验收

1. 工程与存储原型：定义最小内容目录/解析接口，模拟几百 MB 资源、频繁小修改，
   验证保存、版本恢复、复制分享，不把数据库表结构直接暴露给 UI。
2. 多地图与资源闭环：接入现有 Asset Browser；导入一份纹理并用于两张地图，
   重新导入同步更新、重命名/移动保持引用、保存重开、恢复旧版本、移走原文件后
   编译。再覆盖模型/Sprite/声音/天空盒及其依赖，并验证未打开地图与缓存失效。
3. 变换闭环：旋转缩放、面编辑、撤销重做、保存重载和 MAP 导出的结果一致。
4. 模板闭环：跨地图更新、实例覆写、连接隔离、冲突处理与整体回滚。
5. 发布闭环：固定输入快照、依赖收集、批量编译，使用未修改的 CS 1.6 验证。

第一版依次完成这些闭环，架构预留以后参数化对象的扩展位置；具体生成工具
单独评估，不把全部候选建模功能绑定为首版交付条件。
