# TB 原生工程格式设计草案

状态：需求讨论与技术预研；尚未实现。2026-10-28 更新。

## 已确认的产品决策

- 首版以现有 Counter-Strike 1.6 游戏/引擎验证，只修改 TB 和 hltools。
- 一个工程对应一个游戏，包含多张地图、共享资源和多套编译配置。
- 典型规模为几张到十几张地图、几百 MB 资源，主要由个人编辑，分享整个工程文件。
- 日常保存和分享使用一个完整工程文件。
- 使用的纹理、天空盒、模型、Sprite、声音及配套依赖内嵌管理。
- 图片导入自动生成兼容结果，预览确认后采用；额外保存原图以便重新转换。
- 内嵌副本是权威来源，外部修改通过手工重新导入应用。
- 重新导入保留资源身份，所有引用一起更新。
- 预制件跨地图联动，修改模板可更新实例，允许实例局部覆写。
- 第一版版本管理支持版本节点、比较与恢复。
- hltools 的 MAP 源码附加功能已改为显式开启；工程保存与游戏发布分别设计。

以下结构与实施顺序是技术建议，并非用户已经逐项确认的格式规范。

## 工程的内容与身份

工程保存游戏目标、实体定义快照、地图目录、资源库、模板库和编译配置。
地图保存对象树、几何、材质绑定、实体属性、变换、枢轴、图层与编辑状态。
游戏安装路径、编译器可执行文件位置和个人快捷键由本机配置负责。
换电脑后，编辑资源和地图不依赖原机路径；实际运行游戏仍需配置本机安装。

项目、地图、节点、资源、模板与模板子对象使用稳定 ID。显示名称、发布路径、
内容哈希分别建模：内容相同可以共用存储，但不同资源的身份和替换行为仍独立。
现有对象的 link ID 表达关联关系，不直接充当全工程唯一节点 ID。

核心记录建议分为：

| 记录 | 职责 |
|---|---|
| 工程与版本 | 工程身份、格式版本、所需能力、游戏目标 |
| 地图与节点 | 按地图分区的对象树、几何、属性和编辑状态 |
| 资源与内容块 | 资源身份、原文件、兼容结果、内容哈希 |
| 转换配方 | 转换器版本、尺寸、调色板、透明处理等参数 |
| 依赖与引用 | 地图引用、资源配套依赖、手工声明的动态依赖 |
| 模板与实例 | 模板修订、实例关联、子对象身份和覆写 |
| 编译配置 | 选项、工具版本记录、发布目标及路径映射 |

## 对象变换

保存局部几何、对象变换和枢轴，同时保留数值面板的旋转/缩放表达，避免每次
从矩阵重新分解而丢失旋转圈数等编辑意图。MAP 导入使用导入时的几何作为起点，
不猜测无法恢复的历史旋转和缩放。

世界几何由局部几何和父子变换求值，供渲染、拾取和导出使用。面/顶点编辑必须
明确修改哪一层局部几何，不能只在保存时补记数值。零缩放、镜像、非均匀父级
缩放、剪切及纹理锁定要有明确行为，提交变换前验证几何是否合法。
烘焙变换是显式操作，并由同一撤销事务维护几何与变换状态。

## 资源与发布名称

原图、转换配方和兼容结果随资源修订一起保存；转换确认后更新资源并使相关
预览与编译缓存失效。天空盒六面、动画纹理组、模型配套文件作为完整依赖管理。
提供使用位置查询、替换影响预览和显式的未使用资源清理。

内部资源 ID 不直接输出为游戏名称。发布映射必须保留 GoldSrc 纹理特殊前缀、
动画组关系、短名称限制，以及模型、声音等资源的有效游戏路径。同名不同内容
需要显式解决冲突；无法可靠重写的脚本或字符串引用进入诊断，不能猜测改名。

## 预制件与工程级修改

模板是独立定义，实例记录模板修订、变换及按稳定子对象 ID 定位的覆写。
修改模板采用显式模板编辑入口，普通实例编辑默认形成覆写。
支持恢复单项覆写和解除关联。首阶段优先覆盖变换、实体属性和材质覆写；
子对象增删与拓扑覆写需要额外定义冲突规则后逐步补齐。

模板删除了被覆写对象时保留冲突记录，并提供保留、删除或解除关联的处理入口。
重复放置实体组合需要避免 targetname 等内部连接互相串接，同时保留明确的外部
连接；实体引用转换采用已知规则，未知字符串保持原样并提示检查。

共享资源和模板修改属于工程级事务；地图操作保持现有命令语义。跨地图操作
必须整体成功或回滚，并覆盖未打开地图。地图撤销与工程撤销的相互影响需先做
原型验证，防止撤销地图编辑时意外恢复旧的共享内容。恢复日志、自动备份和
运行期撤销记录分别设计，不默认承诺跨重启保存完整撤销历史。

## 存储候选与保存语义

优先验证 SQLite 单文件容器：事务保存变更记录，几何按对象或适当数据块组织，
资源内容按需读取和按内容去重，避免改一个实体就重写全部资源。压缩按内容块
选择，不对已经压缩的资源反复压缩。扩展名暂称 `.tbproj`，尚未定名。

首选验证 rollback journal 的 DELETE 模式，以正常提交后的主文件作为可携带
工程。事务期间可能存在恢复日志；发生中断时由存储层恢复，不能手工删除日志。
编辑器提供生成一致副本的分享/另存入口；正常关闭后可直接复制工程文件。
事务中的普通文件复制不作为一致备份方案。

Ctrl+S 提交完整、一致的工程修订；自动恢复保存到受管理的本地恢复区，恢复后
由用户决定是否写回。保存失败保持脏状态并报告错误，不提前显示保存成功。
历史资源修订按明确保留策略回收，整理空间作为独立操作执行。

容器候选需要验证大资源、小几何更新、磁盘空间不足、中断写入、另存和备份。
SQLite 事务提供存储基础，不能替代项目层的校验、错误处理和故障测试。
当前结论不构成已经完成的性能或可靠性验收。

## 工程版本历史

第一版采用工程内的命名版本节点，提供比较和恢复。以下为建议的具体语义：

- 普通保存更新当前工作状态；创建版本节点由用户显式操作，记录名称、说明和时间。
- 节点记录完整工程的一致状态，包括所有地图、共享资源及其原文件与转换配方、
  模板、实例覆写、游戏目标与编译配置。比较和恢复都不得遗漏共享依赖。
- 历史使用不可变修订和内容块引用，共用未变化的数据。保留节点引用的旧资源
  必须可用，不能被当前资源替换或未使用资源清理覆盖、删除。
- 比较先提供新增、删除、修改的地图、对象、资源、模板及属性摘要；空间叠加等
  可视化比较另作后续交互评估。稳定 ID 用于匹配对象，避免名称变化被误判为重建。
- 恢复前先处理当前未保存内容，并保留恢复前工作状态的安全节点。恢复以同一
  工程事务切换完整状态，保留既有历史节点；单独恢复对象或资源另行评估。
- 节点删除必须显式执行。空间整理仅回收当前状态、保留版本与受保护快照都
  不再引用的数据；自动恢复使用独立保留策略。
- 分享副本建议默认包含当前工程状态及其完整依赖，可选择包含版本历史。
  删除历史的分享副本不应更改原工程。
- 工程内历史、运行期撤销、崩溃恢复与外部备份分别负责长期节点、操作撤回、
  未保存修改恢复与文件级损坏恢复。备份文件必须独立于主工程。

SQLite 的事务与 journal 负责存储一致性，版本节点由应用显式实现。
Git 继续用于 TB/hltools 源码；后续如需要项目 Git 工作流，评估稳定的目录导出
和资源文件映射，再交给 Git/LFS 管理。其导出与回读需要完整保留工程语义。

## TB 与 hltools 的分工

建议抽出不依赖 Qt 的共享工程读取与解析模块，供 TB 和 hltools 使用，统一
版本、引用解析和校验规则。TB 负责编辑、撤销、预览和导入；hltools 从固定
工程修订读取选定地图，将模板和变换展开成可编译数据，并解析工程内资源。
编译期间继续编辑不应改变该次编译的输入。

MAP 导入/导出保留，作为交换和兼容途径。首个集成里程碑可先输出临时 MAP/WAD
接入现有编译链，之后再接直接读取；临时产物不承担工程编辑状态的权威保存。
发布只收集所选地图需要的运行资源，原图、编辑元数据和模板定义留在工程中。

## 现有代码基础

- `mdl::Group` 已有变换矩阵，`NodeSerializer::groupProperties` 已保存分组变换。
- `LinkedGroupUtils` 已有同地图关联更新和实体 protected properties，适合评估
  复用算法，但不是已经实现的跨地图模板与通用覆写系统。
- `BrushNode` 当前以 `Brush` 几何为核心，独立对象变换需要覆盖编辑命令与求值。
- TB 的 `ZipFileSystem` 是读取基础；hltools 的 `create_zip` 当前在内存中构建
  整个 ZIP。二者不直接满足增量工程保存要求。

## 建议的交付顺序与验收

1. 存储与版本原型：模拟几百 MB 资源、频繁小修改，验证保存、恢复、复制分享。
2. 多地图与资源闭环：旧 MAP/WAD 导入、资源内嵌、移走原文件后重新打开与编译。
3. 变换闭环：旋转缩放、面编辑、撤销重做、保存重载和 MAP 导出的结果一致。
4. 模板闭环：跨地图更新、实例覆写、连接隔离、冲突处理与整体回滚。
5. 发布闭环：固定输入快照、依赖收集、批量编译，使用未修改的 CS 1.6 验证。

第一版依次完成这些闭环，架构预留以后参数化对象的扩展位置；具体生成工具
单独评估，不把全部候选建模功能绑定为首版交付条件。
